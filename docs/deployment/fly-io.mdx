# Fly.io

Scrapix runs as **six Fly apps** with GitHub Actions building Docker images and deploying via `flyctl deploy --image`. All services except the Kafka broker scale to zero when idle, giving a baseline cost of ~$18/mo.

## Architecture

| Fly app | Role | VM | Scale-to-zero |
|---|---|---|---|
| `scrapix-redpanda` | Kafka broker (`*.internal` only) | shared-cpu-2x, 1 GB + 10 GB volume | No — broker must stay up |
| `scrapix-api` | HTTP API | shared-cpu-1x, 512 MB | Yes — auto-starts on HTTP request |
| `scrapix-console` | Next.js web UI | shared-cpu-1x, 256 MB | Yes — auto-starts on HTTP request |
| `scrapix-frontier` | URL frontier singleton | shared-cpu-1x, 256 MB | Yes — woken by API on `POST /crawl` |
| `scrapix-worker-crawler` | Fetcher worker (Chromium) | shared-cpu-2x, 1 GB | Yes — horizontally scalable |
| `scrapix-worker-content` | Content parser worker | shared-cpu-1x, 512 MB | Yes — horizontally scalable |

External dependencies (unchanged): hosted Meilisearch, ClickHouse Cloud, managed Postgres, managed Redis/Dragonfly.

## How scale-to-zero works for workers

Fly's proxy only auto-starts a machine when it sees an incoming TCP connection on a declared port. Kafka consumers don't receive incoming traffic, so:

1. Each worker binary binds port `8081` with a bare-TCP wake listener (implemented in the shared `scrapix-lifecycle` crate).
2. Fly's worker `[[services]]` block declares port 8081 with `auto_stop_machines = "suspend"` and `min_machines_running = 0`.
3. The API binary, on `POST /crawl`, fires a fire-and-forget TCP connect to each worker at `<app>.internal:8081`. Fly sees the connect → autostarts the suspended machine.
4. The worker spins up, joins its Kafka consumer group, rebalances partitions, processes messages.
5. After `IDLE_EXIT_MINUTES` of zero Kafka messages (default 10), the worker exits cleanly with offsets committed. Fly's proxy sees zero connections + no process → suspends the machine.

First-call latency: ~1–3 s from DNS cold. Acceptable for crawl jobs that run for minutes to hours.

## Kafka on Fly

Redpanda runs single-node on Fly with a 10 GB volume. Connectivity between apps uses Fly's private 6PN WireGuard mesh — no public exposure, no TLS/SASL, no add-ons:

```
KAFKA_BROKERS=scrapix-redpanda.internal:9092
```

Topic partition counts (created by `deploy/fly/create-topics.sh`) must match `docker-compose.yml` so that worker horizontal scaling works — max useful worker count per service = its topic's partition count.

## CI/CD

`.github/workflows/deploy-fly.yml` runs on every push to `main`:

1. **Change detection** — `dorny/paths-filter` decides whether to rebuild Rust, Console, or both.
2. **Cargo fmt + check** — fails fast on lint.
3. **Build** — one matrix job per binary (`scrapix-api`, `scrapix-frontier-service`, `scrapix-worker-crawler`, `scrapix-worker-content`), all sharing the same `Dockerfile.fly` multi-target build and the same GHA cache scope (`scrapix-rust`). Images pushed to `ghcr.io/<owner>/<name>:<sha>` and `:main`.
4. **Deploy** — one `flyctl deploy --image` job per Fly app, parallel, using the pre-built GHCR image (no Fly builder).

Only secret required: `FLY_API_TOKEN` (org-scoped deploy token). `GITHUB_TOKEN` handles GHCR auth.

## Horizontal scaling

```bash
flyctl scale count 6 -a scrapix-worker-crawler   # cap: 12 (partitions on scrapix.urls.frontier)
flyctl scale count 3 -a scrapix-worker-content   # cap: 6 (partitions on scrapix.pages.raw)
flyctl scale count 0 -a scrapix-worker-crawler   # back to zero
```

Kafka consumer groups rebalance automatically when machines join or leave. Offset commits are manual (`enable.auto.commit = false`), so the worst-case on scale-down is that in-flight messages get reprocessed by another machine after the 30 s `kill_timeout` window.

`scrapix-frontier` is a **singleton** — never scale it beyond 1. The bloom filter is per-process state.

## First deploy

See `deploy/fly/README.md` for the full runbook. At a high level:

1. Create the six Fly apps (`flyctl apps create …`).
2. Create the 10 GB volume for Redpanda.
3. Deploy Redpanda and run `./deploy/fly/create-topics.sh`.
4. Set secrets per app (`flyctl secrets set …`).
5. Push to `main` — CI builds and deploys.
6. Add custom domains (`flyctl certs add …`) and flip DNS from Heroku.

## Environment variables

See `deploy/fly/README.md` for the complete list. The tuning knobs specific to scale-to-zero:

| Variable | Apps | Purpose |
|---|---|---|
| `WORKER_WAKE_HOSTS` | `scrapix-api` | Comma-separated `host:port` list of workers to wake on `POST /crawl`. Unset = no fan-out (local dev). |
| `IDLE_EXIT_MINUTES` | workers | Minutes of no Kafka messages before clean exit. `0` disables the watchdog (always-on workloads). |
| `WAKE_PORT` | workers | Port the bare-TCP wake listener binds to. Default `8081`. |

## Rollback

Two paths:

1. **Redeploy a previous image** — `flyctl releases -a scrapix-api` lists SHAs; `flyctl deploy --image ghcr.io/.../scrapix-api:<prev-sha> -a scrapix-api` rolls back.
2. **DNS flip** — during the initial cutover window, Heroku stays warm. Revert the A/AAAA records at the registrar and traffic returns to Heroku within the TTL (60 s).
